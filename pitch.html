Security by design

Read-only first. Least privilege always.

SnowLens analyzes metadata and telemetry, not customer data. It should never need ACCOUNTADMIN, table contents, or unrestricted SQL execution.

Advisory mode · MVP

Read usage, metadata, and optionally governance history. Detect opportunities and produce evidence, but never modify Snowflake.

Autonomous mode · later

Only after approval: a separate, scoped execution role can change warehouse properties or suspend/resume workloads.

USAGE_VIEWER

Query history, warehouse metering, load, storage, tasks, and historical consumption.

OBJECT_VIEWER

Databases, schemas, tables, views, warehouses, and object metadata.

GOVERNANCE_VIEWER

Access history and object usage relationships. Recommended for advanced analysis.

ORGANIZATION_USAGE_VIEWER

Cross-account organization usage for broad discovery and cost rollups.

ORGANIZATION_ACCOUNTS_VIEWER

Account inventory so one integration can map the Snowflake footprint.

ORGANIZATION_BILLING_VIEWER

Billing and monetary context for financial ROI and budget explanations.

Sensitive SQL text stays inside the enterprise: parse and sanitize it into features before any explanation layer sees it. Never grant the AI direct account-level execution.

For developers

How SnowLens actually works.

Under the pitch is a deterministic pipeline: pull telemetry, normalize it into one cost model, extract features, detect waste with rules and statistics, simulate alternatives, then score, recommend, execute, and verify.

The optimization pipeline

Each stage is inspectable and testable in isolation — nothing is a black box.

Ingest telemetry on a schedule

Scheduled jobs read SNOWFLAKE.ACCOUNT_USAGE and ORGANIZATION_USAGE into a staging store. Historical views span 365 days; near-real-time uses the Information Schema (7 days).

Normalize into one cost model

Heterogeneous rows collapse into a warehouse-agnostic model in credits, bytes and seconds, keyed by account → warehouse → user → query.

Extract features

Compute utilization, idle %, queue time, scan/return ratio, spillage, cache hit, pruning and frequency. SQL is parsed to an AST locally with sqlglot — raw query text never leaves the boundary.

Detect candidates

A rule engine plus statistical baselines flag idle or oversized warehouses, SELECT * scans, spillage and cost regressions against a rolling baseline.

Simulate the what-if

The cost model projects credits, dollar savings and predicted P95 latency for each alternative size, auto-suspend value or query rewrite.

Score confidence & risk

Every candidate carries confidence (data volume, variance) and risk (SLA tier, blast radius) so the backlog is sortable and defensible.

Emit an opportunity

A structured object captures evidence, savings, confidence, risk and the exact Snowflake privilege the change would require.

Approve & execute

The policy engine routes to human approval; a separate scoped role runs an idempotent ALTER with prior state stored for rollback.

Verify the outcome

Before/after windows are compared and realized savings are written to the ledger — the only number ever labelled “verified”.

Inside the detection engine

Rules and statistics do the heavy lifting; ML and the LLM are additive, not load-bearing.

Rule engine

Deterministic thresholds catch known waste patterns first — cheap, explainable, and free of model risk.

Statistical baselines

Rolling means and percentiles per warehouse and query surface drift, spikes and regressions.

Anomaly detection

Lightweight ML flags cost and behaviour outliers that static thresholds miss.

Cost & simulation model

Maps credits to dollars and predicts the impact of a size, auto-suspend or rewrite change.

Sanitized LLM layer

Explains the “why” from extracted features only — it never sees raw SQL, PII or table data.

Confidence & risk scoring

Turns evidence volume and SLA sensitivity into a score that gates whether automation is allowed.

How a recommendation is computed

Illustrative — detection is SQL over usage views, estimation is a transparent formula.

Detect · under-utilized warehouse

-- persistently idle / oversized warehouses
SELECT warehouse_name,
       AVG(avg_running)     AS active_clusters,
       AVG(avg_queued_load) AS queue_load,
       SUM(credits_used)    AS credits_30d
FROM   account_usage.warehouse_load_history
JOIN   account_usage.warehouse_metering_history
       USING (warehouse_name)
WHERE  start_time > DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP  BY warehouse_name
HAVING active_clusters < 0.40   -- under-utilized
   AND queue_load     < 0.05;  -- no contention

Estimate · savings, latency, confidence

# credits -> dollars, then the what-if
size_rank  = {XS:1, S:2, M:4, L:8, XL:16, 2XL:32}
target     = one_size_down(current)
saving_usd = credits_30d * (1 - target/current) * price
pred_p95   = latency_model(features, target)   # regression
confidence = f(days_observed, variance, n_runs) # 0..1
risk       = g(sla_tier, queue_headroom, scope) # low/med/high

Detect · query waste

-- scans terabytes to return kilobytes, runs often
SELECT query_id, user_name, warehouse_name,
       bytes_scanned,
       rows_produced,
       bytes_scanned / NULLIF(rows_produced, 0) AS scan_ratio,
       COUNT(*) OVER (PARTITION BY query_hash)   AS monthly_runs
FROM   account_usage.query_history
WHERE  start_time > DATEADD('day', -30, CURRENT_TIMESTAMP())
QUALIFY scan_ratio   > 1e6   -- ~1M:1 waste
    AND monthly_runs > 500;  -- frequent

Signal → opportunity

  • The flagged row becomes an opportunity with estimated_saving, confidence and risk.
  • sqlglot rewrites SELECT * into projected columns and re-estimates bytes scanned.
  • The LLM turns the feature vector into a plain-English rationale — never touching raw SQL.
  • Nothing runs until a human approves; execution uses a scoped role and is idempotent.

Technical intricacies to plan for

The details that decide whether this passes an enterprise security and platform review.

Views are not real-time

Account Usage has latency and a 365-day window; use the Information Schema (7 days) for near-real-time. Design two ingestion paths.

Query text is sensitive

Parse to an AST and sanitize before the LLM. Raw SQL and table data never leave the enterprise boundary.

Estimates are not guarantees

Everything pre-change is “predicted”. Only the measured before/after delta is recorded as “verified”.

Idempotent & reversible

Every executed ALTER is safe to re-run and stores prior state, so any change can be rolled back cleanly.

Least privilege by default

Read-only roles for analysis; a distinct scoped role for execution; ACCOUNTADMIN is never required.

Org vs account scope

ORGANIZATION_USAGE finds the expensive accounts; ACCOUNT_USAGE explains them. One service identity maps the whole footprint.
